# App help audit

## The plan this serves

Help is a book under the **About** section, with in-context help reached from the screens themselves.

**The book**
- Addresses are `help/<section>#feature`: one page per section, one anchor per feature.
- Every feature has an anchor. The anchor id is stable and is what the rest of the app links to.
- Entry: the About page links to the book (today a single `how-to.html`, generated by `Site.how_to_page` from `how_to_*` interface messages).
- Position: the pages sit under About. Their Back and trail go to About (see *About page* in `framework/docs/FRAMEWORK.md`).

**In-context help**
- App features and tiles carry a small help icon. The icons are **hidden** by default.
- A **help icon in the left-hand rail** (the 4th slot from the bottom, above the edit-order spanner, About and Settings) toggles them. Pressing it reveals every in-context icon on the screen.
- Pressing a revealed icon opens an **overlay tile** that loads the text of `help/<section>#feature` and can be dismissed. The text is the book's text, not a copy.
- The icons are question marks. Touching one opens a sheet with **What's this?** first and **Report a problem** second. The rail button is therefore "ask about this", and it replaces the separate report-issue flag (`docs/TODO.md` 3.7).
- **Report a problem** builds an email with `mailto:`: the context the app adds is at most **256 characters** (page and section, anchor, version, language pair and direction), shown in a preview with *Open email* and *Copy*. Nothing is sent in the background. Longer context is a sign of too much complexity, so cut it and do not raise the limit.
- Each icon names the anchor it opens (for example a `data-help="<section>#<feature>"` attribute), so the book and the screen cannot drift apart.

**Reader and language**
- Reader: someone holding a phone who has just met a control and wants to know what it does. Help is judged on whether it answers that in a few seconds.
- Every help text exists in both languages of the pair, Welsh first. The Welsh is a draft until a fluent speaker checks it (`docs/REVIEW.md`).

This skill does not write the help or the icons. It finds what is missing, wrong or stale, and records it. Until the mechanism exists, "no icon" and "no anchor" are expected findings: record them once as framework work, then audit feature by feature.

## Step 1: Inventory the features

Build a list of everything a person can see or do. One line each, with its source.

1. **Pages and screens.** Read `framework/phrasebook/site.py`: home, group, topic, settings, about, how-to, sources, and the lookup card. Confirm against `dist/*.html` (run `python build.py` if `dist/` is stale).
2. **Controls.** Rail buttons (search, Back, About, Settings gear, edit-order spanner), the Cy|En toggles, the pager, jump links, "also heard" chips, regional-form markers, the Share button.
3. **Settings.** Every group and choice in `Site.settings_page`: view mode, accessibility level, colour schemes, order, tile layout reset, regional forms.
4. **Gestures and keys.** From `framework/phrasebook/assets/nav.js`, `search.js`, `arrange.js` and `app.js`: arrows, Home/End, Backspace, `/` for search, Escape, drag to go back, tap-to-move and drag-to-move tiles, edge-swipe exemption.
5. **Reading aids.** Level markers on tiles, section order lines, listen-first rows (first language leads), related-topic tiles, source notes.
6. **System behaviour.** Offline use and install (`sw.js`, `manifest.json`), saved preferences and what is stored on the device, what happens without a script.
7. **Project features.** Anything the edition adds: the About sections in `content/<project>/editions/<name>.json`, project pages, palettes, regional varieties.
8. **Planned features** in `docs/TODO.md` and `framework/docs/TODO.md` marked done recently. Features that are not built do not need help yet.

Use `FRAMEWORK.md` as a map, not as the truth. Where it and the code disagree, the code wins, and the disagreement is a finding.

## Step 2: Inventory the help

Read everything that explains the app to a reader.

0. The book, once it exists: every `help/<section>` page and its anchors, and every `data-help` (or equivalent) attribute in the built pages. Build two lists: **anchors** (what the book documents) and **icons** (what the screens point to).
1. Interface messages `how_to*`, `about*`, `*_lede` and `*_title` in `framework/phrasebook/messages/en.json`, and the same keys in `content/<project>/packs/<code>/pack.json` under `ui` (the Welsh).
2. `about_page` in the edition JSON, both languages, including any section with `"status": "development"` (held back from release, so it is not help a reader can see).
3. The built `dist/how-to.html` and `dist/about.html`, which show what a reader gets.
4. Text on the screen itself that explains a control: leads, hints, `aria-label`s, the edit-order bar.
5. Checklist items in `docs/TODO.md` that say "put X in the how-to page". These are known gaps. Fold them into the new list and say where they came from, so the old line can be ticked off.

## Step 3: Compare

For each feature from Step 1, find its help from Step 2 and rate it:

| Rating | Meaning |
|---|---|
| **ok** | Explained where a reader looks, in both languages, and correct. |
| **missing** | Nothing explains it. |
| **thin** | Mentioned, but not how to do it, or not for both input kinds (touch and keyboard). |
| **stale** | The help describes behaviour the code no longer has. |
| **one language** | Present in English only, or Welsh only. |
| **unreachable** | Exists, but cannot be found from About or from the control. |
| **no anchor** | The feature has no `help/<section>#feature` entry. |
| **no icon** | The feature has an anchor, but the control or tile has no in-context icon. |
| **broken link** | An icon names an anchor that does not exist, or an anchor is never linked from any icon. |
| **no help needed** | Obvious or self-explaining. Say why in one phrase. Keep this list short and honest. |

Judge each help text against these:

1. **Task first.** It starts with what the reader wants to do, not with the component's name.
2. **Touch and keyboard.** Both are covered, as in the existing Moves table, or one is stated as not applicable.
3. **Where it is.** It says where the control is (the narrow bar at the side, the top right), in words that match the screen.
4. **What it remembers.** If the feature saves anything on the device, the help says so and says how to undo it.
5. **Without the script.** If the feature needs the script and the page works without it, the help says what still works.
6. **Same words as the screen.** Labels in the help match labels on the controls in both languages.
7. **One home.** Each fact is written once and linked, not copied across topics.
8. **Short.** A topic fits on one phone screen without scrolling more than a little.
9. **Reads well in the overlay.** The anchor's text makes sense on its own, without the rest of the page, because the overlay shows only that part.
10. **Icon behaviour.** Icons are hidden until the rail's help button is on. Each has an accessible name in both languages, can be reached by keyboard once shown, and the overlay can be dismissed by Escape, a close button and a tap outside it, with focus returned to the icon.
11. **Works without the script.** Where the overlay needs the script, the icon (or the book link) still reaches `help/<section>#feature` as an ordinary link.
12. **Report path.** The sheet offers both actions, the context is 256 characters or fewer and is shown before anything leaves the device, *Copy* works without a mail app, and the address is shown as plain text.

## Step 4: Write `framework/docs/app-help-todo.md`

Create the file if it is missing. If it exists, **update it**: keep done items ticked, keep notes, add new gaps, and tick or remove items the help now covers. Do not recreate it from scratch and lose its history.

Format:

```markdown
# App help: to do

Checked against: <commit short hash>, <date>.
Plan: help is a small site under About, "How to use the app". See `.claude/skills/app-help/SKILL.md`.

## Proposed topics

A list of the help pages the app needs, in the order a reader would meet them. Each has a slug, a one-line purpose and the features it covers.

1. `help/finding-your-way`: tiles, groups, topics, the trail, Back. Anchors: `#tiles`, `#back`, ... Covers: ...

## Framework work for the help mechanism

Checkboxes for the parts of the plan not yet built: the book pages and anchors, the hidden icons, the rail button, the overlay, the `data-help` link between icon and anchor. Tick them as they land.

## Gaps

### Missing
- [ ] **<Feature>.** What it does, where it is, how it is used. Source: `<file>`. Anchor to add: `help/<section>#<feature>`. Icon on: `<control or tile>`. Needs Welsh: yes.

### Thin, stale, one language, unreachable
- [ ] **<Feature>.** <Rating>: <what is wrong>. Where: `<file or message key>`.

## Known and carried over
- [ ] <Item from docs/TODO.md>, moved here. Tick the original there too.

## Checked and fine
A short list of features with ok help, so the next audit does not repeat the work.

## No help needed
<Feature>: <why>.
```

Rules for the file:

- Each item is one checkbox, specific enough to act on without redoing the audit.
- Name the source file or message key so it can be found.
- State if it needs Welsh wording, and whether the English exists.
- Order by what a new reader hits first, not by file.
- No invented behaviour. If a feature is not understood from the code, write "unclear, check <file>" instead of guessing.

## Step 5: Report

Reply with:

1. Counts: features checked, ok, missing, thin, stale, one language, unreachable.
2. The three most important gaps.
3. The file path written or updated.
4. Anything in `FRAMEWORK.md` that disagreed with the code.

## Rules

- **Read-only on the app.** Write only to `framework/docs/app-help-todo.md`. Do not edit messages, the edition or code. If a quick fix is obvious, list it as an item.
- **The framework holds no language.** Help wording for Welsh belongs in the project pack, English default text in the framework catalogue. Say which an item belongs to.
- **Welsh stays unverified.** Never mark Welsh help as checked. Add new Welsh to the `docs/REVIEW.md` list as a separate item.
- **No named storms.** Keep storm names out of examples (see memory `no-storm-names`).
- **Placeholders are not gaps.** Held-back sections and the one-word Everyday > Food and drink page are scaffolding. Do not flag them.
- **Commit rules.** If asked to commit, use the user's identity only. No attribution lines.
